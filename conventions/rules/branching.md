# Branches and merging

Rules only. For *why* any of this is the way it is, see
[`../background/git-workflow.md`](../background/git-workflow.md).

## Quick reference

```
Branch:       <type>/[<issue>-]<slug>        issue number optional
              feature/12-oauth-token-refresh
              fix/null-cart-total
              fix/31
              chore/bump-eslint-9

Branch from:  main
Updating:     rebase onto main — never merge main into your branch
Landing:      pull request into main, "Create a merge commit" — never squash or rebase merge
```

Two questions settle the type:

1. **Would this appear in release notes if it shipped alone?** No → `chore`.
2. **Could a user have done this at all before?** No → `feature`. Yes, but it was worse →
   `enhancement`.

## Branch naming

**Format:** `<type>/[<issue>-]<slug>`

| Element | Rule |
|---|---|
| **Type** | Required. One of `feature`, `enhancement`, `fix`, `chore`. Nothing else. |
| **Issue** | Optional. The GitHub Issue number, digits only — `12`, never `#12` or `GHI-12`. Always the first segment after the slash. |
| **Slug** | Lowercase, kebab-case, short. A memorable handle; it need not match the issue title. |
| **Length** | ~50 characters total. |

**A branch needs an issue number or a slug, never neither.** `fix/31`,
`fix/null-cart-total` and `fix/31-null-cart-total` all pass; a bare `fix/` does not.

### The four types

| Type | Use it when | Example |
|---|---|---|
| `feature` | A capability that did not exist before. | `feature/12-oauth-token-refresh` |
| `enhancement` | A capability that existed, now better — faster, clearer, more complete. | `enhancement/faster-search` |
| `fix` | Something was broken. | `fix/null-cart-total` |
| `chore` | Everything else — deps, tooling, config, docs, refactors, tests. No user-visible change. | `chore/bump-eslint-9` |

There is no `docs`, `refactor`, `test`, `perf`, `hotfix`, `release`, `revert`, `style` or
`wip` type. Urgency is a label, not a prefix.

**A chore pull request is not automatically low-risk.** `chore/reword-readme` and
`chore/extract-payment-service` look identical in a branch list. Chore pull requests that touch
application code get a real review.

### Branches exempt from the convention

| Kind | Form | Notes |
|---|---|---|
| **Mainline** | `main` | The only long-lived branch. |
| **Reverts** | `revert-<n>-<branch>` | Generated by GitHub's revert button. Don't rename it. |
| **Dependabot** | `dependabot/**` | Machine-generated; the prefix isn't configurable. |

## Issues

**GitHub Issues is the only tracker.**

- **Write `Closes #12` in the pull request body** to close an issue on merge. The issue number
  in a branch name does not close anything.
- **Open technical work through the *Technical debt* form.** It requires what leaving the
  problem alone costs. Blank issues stay enabled for anything the form doesn't fit.

## Branching model

`main` is the only long-lived branch, and every change reaches it by pull request.

- **Always branch from `main`.**
- **Never commit to `main` directly.** A ruleset blocks it — see
  [`../../scaffold/README.md`](../../scaffold/README.md).
- **A branch is deleted once it merges.** *Automatically delete head branches* is on.

## Merging

**Every pull request lands as a merge commit.** Squash and rebase merging are disabled, so
*Create a merge commit* is the only option.

Repository settings, applied by `scripts/configure-repository.sh`:

| Setting | Value |
|---|---|
| Allow merge commits | **Checked** |
| Allow squash merging | **Unchecked** |
| Allow rebase merging | **Unchecked** |
| Default commit message for merge commits | **Pull request title and description** |
| Automatically delete head branches | **Checked** |

And a ruleset on `main`:

| Rule | Value |
|---|---|
| Require a pull request before merging | On, 0 required approvals |
| Allowed merge methods | Merge only |
| Require status checks to pass | `Branch name`, `Commit messages` |
| Block force pushes | On |
| Restrict deletions | On |
| Bypass list | Empty |

## Rebasing

**Rebase your working branch onto `main`. Never merge `main` into your working branch.**

```bash
git config --global pull.rebase true
git config --global branch.autoSetupRebase always
```

| Situation | Do this | Not this |
|---|---|---|
| Branch is behind `main` | `git pull --rebase origin main` | `git merge main` |
| Pull request shows "This branch is out-of-date with the base branch" | Rebase locally, then push | Click **Update branch** in the GitHub UI |

**Pushing a rebased working branch needs `git push --force-with-lease`.** That is expected on
your own unshared branch, and never allowed on `main`. If someone else has pulled the branch,
tell them first.

This does not conflict with the merge-commit rule above: `pull.rebase` governs how you update
your own branch, merge commits govern how pull requests land. Rebase locally, merge on the way
in.
